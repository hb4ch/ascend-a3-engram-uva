先看实验对象：三类执行路径，七个实现版本

统一任务：输入主存 token IDs、历史 token 和 mask，生成两层 Engram BF16 查表结果，最终放在 HBM。不包含后续投影、门控、卷积或完整模型。

Ascend C 原版、分块串行、流水 8 行、流水 16 行和 Triton UVA 都属于第三类；它们不是五种不同的数据部署方式。

① CPU 查表，NPU 反量化

CPU 算 hash 得到行号 → CPU 从 DDR 完整 INT8 表收集行 → 写入连续 pinned DDR 缓冲区 → 显式 H2D 复制 INT8 行和行号 → NPU 从 HBM 完整 scale 表收集 scale → NPU 反量化，输出 BF16 到 HBM。

CPU 收集使用 NumPy take；NPU 收集 scale 使用 torch.index_select；反量化使用上游 Triton 算子。CPU 不收集 scale，也不把完整 INT8 表搬到 HBM。

② CPU 查表并反量化，NPU 只接收结果

CPU 算 hash 得到行号 → CPU 从 DDR 收集 INT8 行和对应 scale → CPU 反量化并转换为 BF16 → 将 BF16 结果复制到 HBM。

这条路径需要在 DDR 读取 scale。NPU 不执行 hash、查表或反量化，只接收结果；因此不能简称为“完全没有搬运的全 CPU”。

③ NPU 算 hash，通过 UVA 直接查 DDR 表并反量化

显式 H2D 复制 token IDs 和 mask → NPU 算 hash → NPU kernel 经映射地址直接读取 DDR 的 INT8 行，并读取 HBM scale → NPU 反量化，输出 BF16 到 HBM。

UVA 并非没有搬运。它省掉 CPU 收集到中间缓冲区、再显式 H2D 的过程，INT8 行仍然需要从 DDR 被设备读取。本类内部比较旧 Ascend C、分块串行、两个双缓冲流水版本和上游 Triton UVA。

搬运量：每 token、每层 24 行，每行 256 个 INT8。① 两层显式复制 12,288 字节 INT8 + 384 字节 INT64 行号 = 12,672 字节（约 12.4 KiB）；② 两层显式复制 24,576 字节 BF16。当前不去重。③ 显式复制 token/mask，此外由 kernel 读取 DDR INT8，不能只统计显式 H2D 就声称搬运量接近零。

执行顺序：显式 H2D 使用 non_blocking copy；同一 stream 保证依赖顺序，计时终点同步，确保结果可用。这不代表跨请求搬运与计算已经流水重叠。

这个对比公平到什么程度？

可以比较当前三种实现的整条路径成本：相同真实权重、查询、输出精度与起止点，各自必要的 hash、搬运、计算和终点同步都计入；一次性装载权重都不计时。三类都保留完整 HBM scale 以统一容量条件，② 实际计算另读取主存 scale。

不能据此比较 CPU/NPU 或 Ascend C/Triton 的性能上限：CPU gather 是 NumPy 参考实现，未充分优化、未绑定 NUMA；Ascend C 和 Triton 的 Python 发射开销不同。② 还改变了 scale 的读取位置。固定查询预热和后台权重复制也限制结论外推。

① 与 ③ 最接近“CPU 中转与 UVA”的对照，但不只是 UVA 一个变量：hash 执行位置也从 CPU 换成 NPU。因此总时延差不能全部归功于 UVA。当前报告定位是执行方案的 E2E 比较，不是孤立变量的 UVA 收益测量。

复现条件与适用边界
  • 每 shape、每路径预热 5 次；无阶段打点 50 次、带事件打点 20 次；路径顺序随机交错，减少顺序偏差。
  • 真实层 1 和 14，完整约 183 GiB 表同时驻留；不是 HBM 小表，也不是稀疏假权重。
  • 固定随机种子 20260918，固定 query 重复预热；本轮不是随机冷页、长时间并发或多卡 fan-out 测试。
  • CPU 使用 8 线程；未做 NUMA 绑定。后台权重分发可能争用内存／磁盘，不是机器极限值。
  • Hash 包含 token 压缩、3-token 历史和 mask 失效边界。所有性能测试前进行两层 BF16 逐元素正确性检查。
  • 硬件 Ascend A3 / 单设备 64 GiB HBM，CANN 9.1.0，torch_npu 2.12.0。
